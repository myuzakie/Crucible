# Crucible Judge Path

Crucible's product story is:

> AI can write the app. Crucible proves how it actually behaves on Monad.

The primary surface is the Web viewer. The CLI is shown briefly to establish
that the result is generated by a real execution plane.

## Three-minute demo

1. Run the deterministic gate:

   ```bash
   pnpm judge:check
   ```

2. Open the Web verification viewer:

   ```bash
   pnpm --filter @crucible/web dev
   ```

3. On **Journeys**, choose **New User Purchase**, **Settlement**, or **Auction**.
4. Click **Run journey** / **Run verification** and follow the business-step graph.
5. Select the failed step and show the human-readable issue inspector:
   user impact → what happened → why Monad → runtime evidence → suggested fix.
6. Switch to **Runtime Evidence** to show `MND-TIME-001`,
   `MND-FINALITY-001`, and `MND-FUND-001`.
7. Select **Test this fix** to load the paired fixed fixture, then show all
   three checks passing, Passport eligibility, and the verified replay proof.
8. Briefly show the CLI command that can publish the Passport attestation:

   ```bash
   crucible publish-passport passport.json --rpc <rpc> --registry <address>
   ```

The fixture path is deterministic and does not need RPC, a wallet, or an AI
provider. Testnet evidence and registry publication are optional final proof
steps and must use a dedicated funded test wallet.

Generic fixtures such as Buggy mint remain available under **Developer
fixtures** (`?debug=1`). They are useful for testing generic execution and AI
diagnosis, but they are not the Monad runtime verification story.

## What the judge should remember

Crucible does not claim that a generic EVM pass means Monad readiness. It
connects a real user journey to runtime evidence, explains the user impact,
proves the fix by replay, and produces a version-bound Runtime Passport.

For the detailed UI flow, Monad protocol context, test commands, and
troubleshooting, see [docs/CRUCIBLE_RUNTIME_GUIDE.md](docs/CRUCIBLE_RUNTIME_GUIDE.md).
